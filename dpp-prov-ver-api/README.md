# DPP-Prov-Ver API

A **synchronous Spring Boot REST API** for the Java Hyperledger Fabric DPP-Prov-Ver chaincode.

## Prerequisites

- JDK 21 and Maven 3.9+;
- running Hyperledger Fabric 2.5 test-network with channel `dpp-prov-ver-channel`;
- deployed chaincode `dpp-prov-ver-chaincode` compatible with the current `DppProvVerContract` façade;
- Org1 user enrollment certificate, private key, and peer TLS CA as generated by Fabric test-network.

**Deployment of the chaincode is out of scope here:** follow
[`../dpp-prov-ver-chaincode/README.md`](../dpp-prov-ver-chaincode/README.md).

## Configure

`application.properties` defaults to `Org1MSP`, `localhost:7051`, and `peer0.org1.example.com`.
Point `FABRIC_TEST_NETWORK` to the **absolute path** of `fabric-samples/test-network`
containing `organizations/`:

```bash
export FABRIC_TEST_NETWORK=/absolute/path/to/fabric-samples/test-network
# Optional: export FABRIC_PEER_ENDPOINT=localhost:7051
# Optional: export FABRIC_OVERRIDE_AUTHORITY=peer0.org1.example.com
# Optional: export MSP_ID=Org1MSP CHANNEL_NAME=dpp-prov-ver-channel CHAINCODE_NAME=dpp-prov-ver-chaincode
```

The Gateway connection is opened lazily on the first blockchain request, so the server can
start without a running Fabric network. The `GET /api/health` check does **not** test Fabric connectivity.
The server reuses its Gateway and gRPC connection across requests rather than reconnecting on
every transaction. This matters for measuring throughput and MVCC contention.

## Start

```bash
mvn clean test
mvn spring-boot:run
```

- Swagger UI: <http://localhost:8081/swagger-ui.html>
- OpenAPI JSON: <http://localhost:8081/v3/api-docs>
- HTTP health: <http://localhost:8081/api/health>

## REST endpoints

| HTTP | Path | Chaincode method | Notes |
|---|---|---|---|
| `POST` | `/api/actors` | `createActor` | Creates Actor; generated UUID if `id` omitted |
| `PUT` | `/api/actors/{id}` | `updateActor` | Full document update |
| `GET` | `/api/actors[/{id}]` | `getAllActors` / `readActor` | |
| `POST` | `/api/assets` | `createAsset` | Chaincode `Asset`, **not** demo name/owner/status model |
| `PUT` | `/api/assets/{id}` | `updateAsset` | Immutable identity fields must match |
| `GET` | `/api/assets[/{id}]` | `getAllAssets` / `readAsset` | |
| `POST` | `/api/passports` | `createDigitalProductPassport` | Root asset must exist |
| `PUT` | `/api/passports/{id}` | `updateDigitalProductPassport` | Root asset immutable |
| `GET` | `/api/passports[/{id}]` | `getAllDigitalProductPassports` / `readDigitalProductPassport` | |
| `POST` | `/api/events` | `submitEvent` | INSTALL, REMOVE, INSPECT, REPAIR, REUSE, CORRECT |
| `GET` | `/api/events[/{id}]` | `getAllLifecycleEvents` / `readLifecycleEvent` | |
| `GET` | `/api/passports/{id}/state?effectiveTime=...` | `reconstructState` | Only `asOfPosition=0` supported |
| `GET` | `/api/containment-intervals[/{id}]` | `getAllContainmentIntervals` / `readContainmentInterval` | Read only |
| `GET` | `/api/inspections[/{id}]` | `getAllInspections` / `readInspection` | Read only |
| `GET` | `/api/decisions[/{id}]` | `getAllAcceptanceDecisions` / `readAcceptanceDecision` | Read only |
| `GET` | `/api/conflicts[/{id}]` | `getAllConflicts` / `readConflict` | Read only |
| `POST` | `/api/conflicts/{id}/resolve` | `resolveConflict` | Confirm an existing decision |
| `GET` | `/api/resolutions[/{id}]` | `getAllResolutions` / `readResolution` | Read only |

Derived records (`ContainmentInterval`, `Inspection`, `AcceptanceDecision`, `Conflict`, `Resolution`)
have no direct CREATE/UPDATE REST endpoints because the deployed chaincode does not expose them.
`LifecycleEventData` is an embedded event input object, **not** a ledger entity.
`componentId`, `hostId` and `assetId` reference `Asset.id`.

**Supported lifecycle types:** the enum contains extra values, but the current chaincode implements
only INSTALL, REMOVE, INSPECT, REPAIR, REUSE and CORRECT. Direct `createLifecycleEvent` is obsolete.

## Example calls

From the backend project directory, run once on a fresh set of sample IDs:

```bash
curl -sS -X POST http://localhost:8081/api/actors -H 'Content-Type: application/json' -d @examples/01-actor.json
curl -sS -X POST http://localhost:8081/api/assets -H 'Content-Type: application/json' -d @examples/02-host-asset.json
curl -sS -X POST http://localhost:8081/api/assets -H 'Content-Type: application/json' -d @examples/03-component-asset.json
curl -sS -X POST http://localhost:8081/api/passports -H 'Content-Type: application/json' -d @examples/04-passport.json
curl -sS -X POST http://localhost:8081/api/events -H 'Content-Type: application/json' -d @examples/05-install-event.json
curl -sS 'http://localhost:8081/api/passports/api-dpp-01/state?effectiveTime=2026-10-20T11:30:00Z'
```

**Use unique IDs for repeated runs.** Event `id` and `operationId` are mandatory and preserved
exactly as supplied to support idempotent retries and reproducible concurrency experiments.
The JSON examples use static IDs and therefore **will not** be reusable unchanged on the same ledger.

## Synchronous transaction semantics

Each write creates one Gateway proposal, endorses it, submits it, and **waits for Fabric VALID commit**
before returning HTTP success. `SubmitResponse` includes `transactionId`, `fabricStatus`,
`durationMs` (server-side elapsed milliseconds), and the chaincode `result` where provided.

For `submitEvent`, the response includes `semanticOutcome=ACCEPTED|REJECTED` read from the
committed acceptance decision. **A Fabric VALID transaction may contain a REJECTED semantic
decision**. These two outcomes are not interchangeable.

- Fabric invalid commit (including MVCC conflicts) produces HTTP **409** with a transaction ID
  and the exact Fabric validation code in the error JSON (`stage=COMMIT`).
- Endorsement fails with HTTP **422** (`stage=ENDORSE`); this is **not** a committed semantic REJECTED event.
- Orderer submission / gRPC errors produce HTTP **502** and an error stage.
- Commit-status timeouts are classified as `COMMIT_STATUS_UNKNOWN`; **do not assume the transaction failed
  or retry automatically**. Check transaction status first or use the operation-ID idempotency policy.

These statuses are intended for subsequent JMeter/HTTP-client classification; no concurrency or
performance results are claimed by this repository alone. Any bearer-token authentication must
be implemented before exposing this API outside a trusted laboratory environment.

## Temporal limitations

`GET /api/passports/{id}/state` reconstructs effective-time containment using the latest
accepted interpretation. The global logical sequence was removed; historical-as-known-at
commit positions \(S(\tau,\ell)\) require an **off-chain block projection**, which is
**not implemented** in this backend. Passing `asOfPosition` other than `0` is rejected with HTTP 400.

## Tests

`mvn test` contains unit tests for the synchronous services using mocked Fabric Gateway results.
They require **no** running Fabric network. Deployment and end-to-end behavior must be verified
against a running Fabric 2.5 test-network separately. No JMeter suite is included here.
